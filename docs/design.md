# JobDash 設計方針

転職活動の選考状況を管理する個人用 Web アプリ。ローカル環境で完結し、認証は持たない。
本ドキュメントは機能追加に向けた全体方針と、ユーザーとの合意事項を記録する。

最終更新: 2026-11-14

---

## 1. 前提

- 利用者は 1 人、データ量は少ない（企業数十〜数百件程度）。
- DynamoDB（dynamodb-local）を継続利用する。データ量が少ないため、Query 結果をアプリ側で集計・フィルタしてよい。GSI は使わない。
- 日時はタイムゾーンを持たないローカル時刻文字列で扱い、JST を前提とする。
  - 日付のみ: `YYYY-MM-DD`
  - 日時: `YYYY-MM-DDTHH:mm`
  - 文字列のまま辞書順で比較でき、並べ替えにそのまま使える。
- 時刻の入力は 15 分刻み。ただし取り込んだデータなど刻みから外れた値は保持し、勝手に変えない。

## 2. 技術方針

| 項目                   | 方針                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| リポジトリ構成         | npm workspaces によるモノレポ: `packages/shared`, `backend`, `frontend`                                                                                  |
| 型・バリデーション     | `packages/shared` の **zod スキーマ**を唯一の定義元とする（型・入力検証・選択肢定義）。フロントとバックエンドで型を二重に定義しない                      |
| バックエンド           | Hono。`routes/`（HTTP）→ `repositories/`（DynamoDB アクセス）に分割し、業務ルールが増えたら `services/` を挟む。入力検証は `@hono/zod-validator`         |
| API クライアント       | shared の型を使った薄い fetch ラッパー。Hono RPC は backend の依存がフロントの型チェックに入り込むため採用しない                                         |
| 更新 API               | **PATCH で部分更新**し、`version` 属性による楽観ロックで同時更新を検出する（不一致なら 409）。詳細画面のセクションごとの保存が互いに上書きし合うのを防ぐ |
| フロントのデータ取得   | **TanStack Query**（キャッシュと、更新後の一覧・詳細の再取得）                                                                                           |
| フロントのディレクトリ | 機能単位: `features/<機能>/{components,hooks,lib}`。複数機能で使う UI 部品は `components/ui`                                                             |
| テスト                 | **vitest** に統一。API は `app.request()` を使い、dynamodb-local のテスト用テーブルに対する結合テストにする                                              |
| バックアップ           | 全データの JSON 書き出し・復元を用意する。データ移行の前には必ずバックアップを取る                                                                       |
| カレンダー             | FullCalendar（`@fullcalendar/timegrid`, `daygrid`, `interaction` の MIT ライセンス部分）                                                                 |
| グラフ                 | Recharts                                                                                                                                                 |
| Word 出力              | `docx`                                                                                                                                                   |
| PDF 出力               | 印刷用 CSS を当てたページを、ブラウザの「PDF として保存」で出力する（日本語フォントを埋め込む手間が無い）                                                |

### 2.0 画面の表記とアイコン

- 画面上の表記は「会社」ではなく「企業」に統一する（企業名、企業 URL、企業研究など）。CSV の取り込みでは、以前の「会社名」「会社URL」の列見出しも引き続き認識する。
- ヘッダーのナビとページ見出し（h1）には同じアイコンを付ける（`frontend/components/layout/nav.ts`、`lucide-react`）。ダッシュボードはロゴ「JobDash」から開くので、ナビには置かない。

### 2.1 コード・テストのデータ

- コード、テスト、プレースホルダ、ドキュメントに**実在の会社名と、その URL を使わない**（応募先・エージェント・勤務先など「会社として登場する」名前はすべて架空にする）。
- 技術・ツール・サービス名（Java、AWS、Cloudflare、Claude など）は、スキルや開発環境の記述として使ってよい（2026-11-08 合意）。
- サンプルの利用者像は [sample-persona.md](sample-persona.md) にまとめる。
- ダミーデータの例:
  - エージェント: `○○エージェント`（MA）、`△△エージェント`（SA）、`××エージェント`（BA）
  - 企業: `A社`、`テスト株式会社` など。サンプルデータでは料理名をテーマにした架空の社名（例: 株式会社うどんシステムズ）
  - サンプルの利用者の勤務先: 株式会社おでんシステムズ、すき焼きソフトウェア株式会社
  - URL: `https://agent-ma.example.com/...` など `example.com` 配下

### 2.2 サンプルデータ

- `packages/shared/samples/sample-data.json`（バックアップ形式）をリポジトリで管理する。動作確認と、将来サンプルとして公開するため。
- 内容: エージェント 3 件（○○/△△/××エージェント）、企業 30 社（料理名をテーマにした架空の社名）、ToDo、職務経歴書。内訳は書類選考・不通過 15、一次面接・辞退 2、オファー/内定 2、その他 11（書類選考中、試験/課題、一次〜最終面接の各状態）。URL はすべて `example.com` 配下。
- JSON は `packages/shared/scripts/generate-sample-data.ts` から生成する。内容を変えるときは生成スクリプトを編集して再生成する。
- 日付は 2026-11-09（月）の週を基準に書き、読み込み時に「今日以降で最初の月曜日」の週へ週単位でずらす（曜日・時刻は保つ）。次回アクションと今後の面接は基準週の火曜日以降に置いているので、どの曜日に読み込んでも未来の日付になる（「今日を含む週」に合わせると、日曜に読み込んだとき 1 週間前にずれて期限切れになるため、この方式にした）。
- 相手の対応待ち（日程調整待ち・選考結果待ち）と終了（辞退・不通過）の企業には、次回アクション日時を入れない。
- 企業メモ・エージェントメモには、Markdown で書いた記録の例（情報収集、面接メモ、面談・電話の履歴、表やチェックリスト）を入れる。メモ本文の日付は読み込み時にずらさないため、ずらした後の予定とは一致しない（サンプルなので許容する）。
- `sample.test.ts` が、スキーマへの適合、社名がリストと一致すること、URL が `example.com` だけであること、内訳を検証する。スキーマを変えたときは、このテストが落ちるのでサンプルも更新する。
- フロントエンドからは `@jobdash/shared/sample` で読み込む（他のページのバンドルにサンプルを含めないため、エントリを分けている）。

## 3. データモデル

シングルテーブル `JobHuntingTable`。PK は全アイテム共通の `USER#me`。

| エンティティ | SK               | 備考                                                                                     |
| ------------ | ---------------- | ---------------------------------------------------------------------------------------- |
| 企業         | `COMPANY#<uuid>` |                                                                                          |
| エージェント | `AGENT#<uuid>`   |                                                                                          |
| 職務経歴書   | `RESUME#main`    | 1 件のみ。経歴・プロジェクトは入れ子で 1 アイテムに持つ（上限 400KB に対して十分小さい） |
| ToDo         | `TODO#<uuid>`    | エージェントの ToDo とダッシュボードの ToDo                                              |

全アイテムに持たせる共通属性: `type`（`COMPANY` / `AGENT` / `RESUME` / `TODO`）, `version`, `createdAt`, `updatedAt`（職務経歴書は `createdAt` なし）。
一覧の取得は `PK = USER#me AND begins_with(SK, '<TYPE>#')` の Query で行う（Scan は使わない）。

### 3.1 企業（Company）

```ts
type SelectionPhase = '書類選考' | '試験/課題' | '一次面接' | '二次面接' | '最終面接' | 'オファー/内定';
type ActionStatus = '要日程調整' | '要本番準備' | '要対応' | '日程調整待ち' | '選考結果待ち' | '辞退' | '不通過';

interface Company {
  id: string;
  companyName: string;
  companyUrl?: string;
  agentId?: string; // 未設定 = 直接応募（v3 移行で、自由入力の agent から置き換えた）
  agentJobUrl?: string;
  phase: SelectionPhase;
  action: ActionStatus;
  nextActionAt?: string; // YYYY-MM-DD または YYYY-MM-DDTHH:mm
  details: string; // 企業メモ（企業詳細の企業研究の先頭で編集する）

  // カレンダーの段階で追加
  interviews: { stage: '一次面接' | '二次面接' | '最終面接'; start: string; end: string }[];
  preferredSlots: { start: string; end: string }[]; // 面接希望日時（選考段階の区別なし）

  // 企業研究の段階で追加
  research: {
    motivation: string; // 志望理由
    futureVision: string; // 入社後の将来像
    reverseQuestions: string; // 逆質問
    attractions: string; // 魅力的な点（1 行 1 項目）
    concerns: string; // 不安な点（1 行 1 項目）
    tags: string[]; // 自由入力。先頭のタグをレポートの「（SI）」表記に使う
    interviewCount?: number; // 面接回数。求人情報を見て手入力する
    rating?: 1 | 2 | 3; // 総合評価 = 志望度（★の数）
  };

  type: 'COMPANY';
  version: number;
  createdAt: string;
  updatedAt: string;
}
```

- 「辞退/不通過」はアクションの「辞退」と「不通過」に分ける（合意事項 1）。この 2 つを「終了」とみなし、一覧ではデフォルトで非表示にする。
- `research` は省略可能。未設定の企業は空の値として扱う（`researchOf()`）。PATCH の `research` は項目単位でマージし、`interviewCount` / `rating` は null で消す。タグは前後の空白を除き、重複を除いて順序を保つ（最大 20 個）。
- 企業メモ（`details`）は用途を決めない自由記述のため、Markdown（GFM）で表示する。普段は整形した表示で全文を見せ、「編集」で入力欄（編集／プレビュー）に切り替える。URL は自動でリンクにし（http(s) のみ、新しいタブ）、改行はそのまま改行として表示する。メモ内の生の HTML は表示しない。
- 企業研究のほかのテキスト欄はプレーンテキストのまま。入力に合わせて高さが伸び、全文が見えるようにする（`AutoTextarea`）。
- 企業研究（企業メモを含む）は自動で保存する（保存ボタンは置かない）。テキスト欄はフォーカスが外れたとき・メモの「完了」・入力が 2 秒止まったとき、タグと総合評価は変更した時点で保存する。保存するのは保存済みの値と違う項目すべてなので、失敗した分は次の保存でまとめて送られる。範囲外の面接回数は保存せず、欄の下にエラーを出す。見出しの横に保存状態（保存中・保存しました・失敗と再試行）を表示する。自動保存の処理は `useAutosave`、保存状態の表示は `SaveStatus` に共通化している。アプリ内で画面を移ると残りを保存し、タブを閉じるときは未保存なら警告する。
- 企業詳細の「選考状況の更新」も保存ボタンを置かない。選考フェーズ・アクションは選んだ時点で、次回アクション日時は日付・時刻の組からフォーカスが外れたとき・Enter・「クリア」で保存する（日付欄は年の入力途中にも `0002-11-14` のような値を通知するため、変更のたびには保存しない）。見出しの横に企業研究と同じ保存状態を表示する。
- 同じ企業への更新（PATCH）は 1 件ずつ順に送り、送る時点で最新の `version` を使う（TanStack Query の mutation `scope`）。続けて保存しても自分の更新どうしで 409 にならない。
- 面接は `stage` 付きの配列で持つ。UI では一次・二次・最終の 3 つに限るが、後で段階を増やしてもデータ構造は変えずに済む。

### 3.2 エージェント（Agent）

```ts
interface Agent {
  id: string;
  name: string; // エージェント名
  shortName: string; // 略称（企業一覧などの表示に使う）
  contactName?: string; // 担当者名
  contactEmail?: string; // 担当者メールアドレス
  contactPhone?: string; // 担当者電話番号
  url?: string; // エージェントURL
  memo: string; // エージェントメモ（面談・電話の履歴、メールの記録など）
}
```

- 企業のエージェントは、この一覧から選ぶ。
- エージェントメモは詳細画面の ToDo の下に独立した枠で表示し、企業メモと同じ形式（Markdown 表示、「編集」で入力、自動保存）にする。登録・編集フォームには含めない。エージェントの更新も企業と同じく 1 件ずつ順に送り、最新の `version` を使う。
- 企業が紐づいているエージェントは**削除できない**（合意事項 9）。
- 略称は重複不可（大文字小文字・全角半角を区別せずに判定する）。
- CSV インポートでは、CSV のエージェント列の値ごとに「既存のエージェントに紐づける／新規作成／紐づけない」を選ぶ。既定では略称（次に名前）が一致する既存エージェントに紐づけ、無ければ新規作成する。新規作成ではその値を名前と略称の両方に使う。
- 移行（v3、2026-11-08 適用）では、既存の自由入力の値（4 種類）からエージェントを作成した。名前は略称と同じ値のため、正式名への変更はユーザーが行う。

### 3.3 職務経歴書（Resume）

```ts
interface Resume {
  fullName: string;
  summary: string; // 職務要約
  careers: {
    companyName: string;
    period: { from: string; to?: string }; // YYYY-MM。to が未設定 = 現在
    // 企業詳細（すべて任意の自由入力。「3,000万円（退職時点）」のような注釈も書ける）
    businessDescription?: string; // 事業内容
    listing?: string; // 上場区分（候補: 東証プライム上場 / 東証スタンダード上場 / 東証グロース上場 / 未上場）
    capital?: string; // 資本金
    revenue?: string; // 売上高
    employees?: string; // 従業員数
    employmentType?: string; // 雇用形態
    department?: string; // 所属部署
    interviewNotes: { reasonForJoining: string; reasonForLeaving: string }; // 入社理由・転職理由（出力しない）
    projects: {
      name: string;
      period: { from: string; to?: string };
      overview: string; // プロジェクト概要
      responsibilities: string; // 担当業務
      environment: string; // 言語・環境
      team: string; // チーム構成
      interviewNotes: { hardships: string }; // 面接対策メモ（出力しない）
    }[];
  }[];
  skills: string; // 活かせる経験・スキル
  selfPr: string; // 自己PR
  interviewNotes: { strengths: string; weaknesses: string }; // 出力しない
}
```

- 職務経歴書は 1 つだけ（合意事項 8）。
- 期間は `YYYY-MM` で保存し、出力時は「2020年4月～2021年3月」と日本語で表記する。終了が未設定なら「～現在」。
- 出力形式はプレーンテキスト・Markdown・Word・PDF。面接対策メモは出力しない。レイアウトは当面シンプルでよい。

実装メモ:

- API: `GET /api/resume`（未保存なら空の内容と `version: 0`）、`PUT /api/resume`（文書全体を置き換え。`version` で楽観ロック、0 は初回保存）。
- 出力は共通の中間表現（`resumeBlocks()`）から作る。テキスト・Markdown は shared、Word は `docx` ライブラリ、PDF はプレビューを印刷用 CSS（A4）でブラウザ印刷する。どの形式も未保存の編集内容で出力できる。
- 転職理由は会社ごとに持つ。以前の全体の転職理由（`interviewNotes.reasonForChange`）は、読み込み時（API・バックアップ復元）に直近の会社（在籍中 → 終了年月 → 開始年月の新しい順）の転職理由へ移す。職務経歴が 1 件もないときはそのまま残し、編集画面の全体メモに表示する。
- プレビュー・出力画面で文字サイズを「標準（10.5pt）」「小さめ（9pt）」から選べる（ブラウザごとに保存）。PDF（印刷）と Word に反映する。
- 期間には在籍期間を併記する（例: 2020年4月～2023年9月（3年6か月））。「現在」の期間は今月まで数える。
- 企業詳細は編集画面ではアコーディオン（既定で閉じる。入力の有無とは連動しない）にまとめ、3 段で並べる: ① 事業内容 ② 上場区分・資本金・売上高・従業員数 ③ 雇用形態・所属部署。出力も同じ 3 段で、入力のある項目だけを「ラベル: 値」の形でスラッシュ区切りにして出す（空の段は出さない）。上場区分・雇用形態は候補から選ぶか自由入力。
- 企業詳細の項目追加では、以前のデータの未設定の項目は空文字として読み込む（移行は不要）。
- バックアップに `resume` を任意項目として追加した（以前のバックアップもそのまま復元できるため、スキーマバージョンは 3 のまま）。全データ削除の対象にも含む。
- サンプルデータには、ペルソナ（[sample-persona.md](sample-persona.md)）の職務経歴書を含める。

### 3.4 ToDo

エージェントの ToDo とダッシュボードの ToDo を同じエンティティで持つ（SK = `TODO#<uuid>`）。

```ts
interface Todo {
  id: string;
  title: string; // 項目名
  details: string; // 詳細（空でよい）
  nextActionAt?: string; // YYYY-MM-DD または YYYY-MM-DDTHH:mm
  status: 'open' | 'done'; // 未完了 / 完了
  completedAt?: string; // 完了日時（ISO）。open に戻すと消す
  agentId?: string; // あり = エージェントの ToDo、なし = ダッシュボードの ToDo
  version: number;
  createdAt: string;
  updatedAt: string;
}
```

- エージェントの中に配列で持たない（チェックで完了にする操作が多く、ToDo 単位の更新と楽観ロックにしたいため）。
- ToDo のあるエージェントを削除すると、その ToDo も削除する（確認ダイアログで件数を示す）。企業が紐づいているエージェントは従来どおり削除できない。
- 完了した ToDo は削除せずに残す。
- バックアップに `todos` を任意項目として追加する。全データ削除・サンプルデータの対象に含める。

## 4. 機能仕様と合意事項

### 4.1 カレンダー

- **面接に限ったカレンダー**とする（次回アクション日時などは表示しない。合意事項 7）。
- 登録は企業の詳細画面から行う。「一次面接日時」「二次面接日時」「最終面接日時」「面接希望日時」のどれかを選ぶと、カレンダー登録画面に移り、週表示でドラッグして予定を作る。
- 面接希望日時は 1 社に**複数**登録でき、選考段階（一次・二次）の区別は持たない。
- 面接日時（確定）を登録すると、その企業の面接希望日時はすべて消える。登録済みの面接日時は消さない（例: 一次面接の予定を残したまま、二次面接の希望日時を追加で入力できる）。
- 面接日時を登録したとき、次回アクション日時が未設定なら、面接の開始日時を次回アクション日時にする。
- 面接希望日時はエージェントへの連絡用にプレーンテキストで出力できる。フォーマットは選べる。
  - 例: `11/4（水）17:00開始～20:00終了`
- カレンダー表示画面は週表示がデフォルトで、月表示にも切り替えられる。この画面では編集できない。

実装メモ:

- API: `PUT /api/companies/:id/interviews/:stage`（stage は `first` / `second` / `final`）、`DELETE /api/companies/:id/interviews/:stage?version=N`、`PUT /api/companies/:id/preferred-slots`。面接・希望日時は PATCH では変更できない。
- 上記のルール（希望日時の削除、次回アクション日時の自動設定）はバックエンドの `companyService` が適用する。面接日時を変更した場合も、希望日時は消える。
- 登録画面（`/companies/:id/schedule?mode=first|second|final|preferred`）では、他社の面接と面接希望日時を灰色で表示する（辞退・不通過の企業は除く）。面接日時の登録中は、その企業の希望日時をクリックするとその日時を選択できる。
- 土日・祝日は同じ薄いグレーで表示する（営業日かどうかだけが関心事のため、赤・青は使わない）。祝日の判定は `@holiday-jp/holiday_jp`（2050 年まで収録）を使い、祝日名は表示しない。土日・祝日でも面接は登録できる。今日は背景色を付けず、日付の数字を青い丸で強調する。
- 週の開始は日曜がデフォルト。カレンダー画面と登録画面で月曜開始に切り替えられ、設定はブラウザ（localStorage）に保存して両画面で共有する。
- 戻り先: 企業詳細へ移る画面は `?from=<自分のURL>` を付ける（カレンダー、エージェント詳細）。企業詳細と、そこから開く日程登録画面は、戻るリンクをその URL に向ける。カレンダーは表示中のビューと日付を `?view=&date=` で URL に保持するので、同じ表示に戻れる。`from` は同一オリジンのパス（`/` で始まり `//` で始まらない）だけを受け付ける。
- 希望日時のテキスト書式は、プリセット 4 種類とカスタムテンプレート（`{年}{月}{日}{曜}{開始}{終了}{終了日}`）から選ぶ。選んだ書式はブラウザ（localStorage）に保存する。

### 4.2 エージェント連絡用のテキスト出力

**面接予定**: 今日以降の面接日時を日時順に並べる。タグ・面接回数・面接の段階（一次面接など。面接日時に登録した段階）の表示を個別にオンオフできる。既定はタグ・面接回数がオン、段階がオフ。段階は面接回数の後に（）の中へ出す（例: `A社（SI、面接2回、一次面接）`）。設定はブラウザに保存する。

3 種類（面接予定・選考状況・志望度）とも、企業名の直後に「様」を付けるかどうかを切り替えられる（既定はオフ。例: `A社様（SI、面接2回）`）。

```
11/4（水）16:00 A社（SI、面接2回）

日程調整中
B社（SES、面接2回）
```

- 面接日時の後に、アクションが「要日程調整」「日程調整待ち」の企業を「日程調整中」の見出しの下に企業一覧の並び順で出す。段階は企業の現在の選考フェーズを出す。該当する企業が無ければ見出しごと出さない。
- 企業名の後の（）には先頭のタグ（合意事項 3）、「面接N回」（企業研究の面接回数）、段階の順に「、」区切りで出す。未入力のものは出さず、どちらも無ければ（）ごと出さない（例: `A社（面接2回）`、`A社`）。

**選考状況**: 次の見出しの順に並べる。書類選考の企業は出さない（合意事項 2）。タグ・面接回数の表示をオンオフできる。

| 見出し                | 条件                                                      |
| --------------------- | --------------------------------------------------------- |
| ◇内定                 | フェーズ = オファー/内定（終了以外）                      |
| ◇{フェーズ}結果待ち   | アクション = 選考結果待ち                                 |
| ◇{フェーズ}待ち       | アクション = 要日程調整・日程調整待ち・要本番準備・要対応 |
| ◇{フェーズ}不採用 N社 | アクション = 不通過（社名は出さず件数のみ）               |

- フェーズの見出しは選考が進んでいる順（`SELECTION_PHASES` の逆順）に並べ、同じフェーズでは「結果待ち」を「待ち」より先にする。「不採用」の見出しは最後にまとめる。
- 辞退した企業は既定では出さない。画面のチェックで「◇辞退 N社」を最後に出せる。

**志望度**: 書類選考と、終了（辞退・不通過）の企業を除き、総合評価（★）の高い順に並べる。魅力的な点・不安な点は 1 行 1 項目で「・」を付けて出す。各企業（「◇企業名」）の前には空行を入れる。タグ・面接回数・選考状況（選考状況テキストの見出しと同じ「一次面接待ち」など）の表示をオンオフできる（既定はオフ。すべてオンにすると `◇A社（SI、面接2回、一次面接待ち）`）。

- 対象は「すべての企業／特定のエージェント経由／直接応募」から選べる。
- 総合評価が未入力の企業は志望度に出さず、画面に社名を注記する。
- 文字列の組み立ては `packages/shared/src/reports.ts`（要件の出力例をそのままテストにしている）。

### 4.3 ダッシュボード（トップ画面）

- 「現時点で必要な情報だけを表示する」がコンセプト。コンテンツは 1 つの一覧テーブルのみ。企業一覧は `/companies` に移す。
- 列: 企業名／項目名、エージェント、選考フェーズ、アクション、次回アクション日時。
- 情報源と条件（次回アクション日時の近い順。日時のない ToDo は末尾）:
  - 企業: 次回アクション日時があるもの。辞退・不通過の企業は除く。クリックで企業詳細（戻り先はダッシュボード）
  - エージェントの ToDo: 未完了のもの。選考フェーズ・アクションは空欄。クリックでエージェント詳細
  - ダッシュボードの ToDo: 未完了のもの。選考フェーズ・アクションは空欄。行のチェックで完了、クリックで編集ダイアログ
- 期限切れ・今日の項目は企業一覧と同じように強調する。
- ダッシュボードの ToDo は「ToDo を追加」ダイアログと「ToDo 一覧」ダイアログで扱う。一覧ダイアログからも追加・編集でき、完了した ToDo はこの一覧ダイアログでだけ表示する（完了日時の新しい順）。
- チュートリアル: 企業・エージェント・ToDo がすべて 0 件のときに表示する。
  - 「さっそく始める」: ダッシュボードの ToDo として「エージェントに登録する」を登録する
  - 「まだ考え中」: ダッシュボードの ToDo として「職務経歴書に現在の業務を書く」を登録する
  - 「サンプルを見る」: サンプルデータを読み込む
  - 「キャンセル」: そのブラウザでは再表示しない（localStorage）
- エージェント詳細画面に ToDo の一覧を置き、チェックで完了にできる。追加・編集もここで行う。カレンダーとは関連させない。
- 同じ日時の行は、企業 → エージェントの ToDo → ダッシュボードの ToDo の順に並べる。行の組み立ては `packages/shared/src/dashboard.ts`。
- ToDo 一覧ダイアログの中で追加・編集の表示に切り替える（ダイアログを重ねない）。
- 企業・エージェントの詳細はダッシュボードから開くと、戻るリンクが「ダッシュボードへ戻る」になる（`?from=/`）。

### 4.4 集計

- 選考フェーズのグラフを、全体とエージェント単位で表示する。不採用を含めるかどうかを切り替えられる。
- 表現: フェーズ別の縦棒グラフ。エージェント別は同じグラフを縦軸を揃えて並べる（small multiples）。
- 色: 選考中を青 `#2a78d6`、不採用（不通過）をグレー `#898781` で積み上げる（強調表示）。dataviz の検証スクリプトで CVD ΔE 15.9、通常視 ΔE 17.8、白背景に対するコントラスト 3:1 以上を確認済み。グレーを 2 段階使うと区別しにくいため、辞退はグラフに含めない（件数はタイルで表示）。
- 凡例は系列が 2 つのとき（不採用を含める場合）だけ表示し、各棒の上に合計を出す。ホバーで内訳を表示し、「表で表示」で同じ数値を表でも確認できる。

## 7. 合意の記録（2026-11-08）

1. 「辞退/不通過」はアクションの「辞退」と「不通過」に分ける。
2. 「〇〇待ち」の見出しは、フェーズ × アクションの組み合わせで決める。書類選考は出力に入れない。
3. 会社名の横の（）表記には、先頭のタグを使う。
